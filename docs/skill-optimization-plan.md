## 一、噪声样本设计（迭代启动前的新门槛）

### 1.1 为什么需要

当前「3 样本启动迭代」的根本缺陷：在 3 张**精挑的干净样本**上优化技能，等于在训练集
上自评好坏 → **过拟合这 3 张**，对该国通用票据无泛化保证（ADR Context 已分析）。

ReflACT 的解药是**留出验证门**（candidate 只有在 held-out 上严格变好才接受）。但门要有
意义，必须有一批**有标注、且分布多样**的 held-out 样本 —— 这正是「噪声样本」的角色：

- **3 anchor 样本** → 训练信号（技能必须把这几张做对）；
- **N 噪声样本** → held-out 验证集（Gate 在它上面判一条 edit 是否泛化）。

「噪声」= **故意随机/多样**（不同开票方、版式、税率、跨页、扫描质量），用来把技能暴露在
真实分布下，而不是 3 张樱桃。

### 1.2 客户侧成本控制（关键 UX）

噪声样本需要 GT 才能进 Gate，但**不要求从零标注**：

1. 客户上传 N 张噪声样本 → **自动用当前技能 OCR**；
2. 走**现有「已审视」复核流**：客户只**快速纠错**（改错值、勾「无此字段」），不逐字段从头填；
3. 复核后这 N 张即成 held-out val。

> 可选增强：允许其中一部分**完全不标注**，仅用作「覆盖率/自洽性」信号（输出是否 schema 合法、
> 跨样本字段集是否稳定），进一步降低客户成本。但**精度 Gate 只用已复核的那部分**。

### 1.3 推荐样本量 N（含依据）

留出 Gate 的判别力取决于 val 规模。在**零容忍字段级评分**（对/错二值）下，n=10 的 val
单字段比例的 1σ 噪声约 ±15pp，n≈20 降到 ±11pp；**soft 评分**（字段级部分分，连续）所需更少
（n≈5–6 即可分辨）。训练侧 SkillOpt minibatch M 通常 4–8。综合客户成本与判别力：

| 档位 | 噪声 N | 总确认样本(3+N) | 切分(train/val) | Gate 指标 | 说明 |
|---|---|---|---|---|---|
| 下限（冒烟） | **7** | 10 | 6 / 4 (留一法) | soft | 能跑通，判别力勉强 |
| **推荐（默认）** | **9–12** | **12–15** | 8 / 4–5 或滚动留一 | soft（少样本）/ mixed | 判别力与成本最佳平衡 |
| 充分 | 15–20 | 18–23 | 滚动 | hard 可用 | 收益递减起点 |
| 过量 | >22 | >25 | — | — | 成本/时延不划算，不建议强制 |

**建议产品默认 `N = 9`（总 12 张），最低强制 `N = 7`（总 10）。**

> ✅ **实测确认（2026-06-28，`eval/noise_scan_jp.py`）**：OCR 24 张真实 Japan-inv val（qwen3-vl-plus，
> 公平字段 10 个），单样本 soft sd=0.132；bootstrap 重采样测 val 均值估计的 ±95% 半宽随 n：
>
> | n（噪声） | 3 | 6 | 8 | **9** | 12 | 16 | 20 |
> |---|---|---|---|---|---|---|---|
> | val 估计 ±95% 半宽 | 14.9pp | 10.4pp | 9.2pp | **8.8pp** | 7.4pp | 6.6pp | 5.9pp |
>
> 典型 1/√n 曲线、无尖锐肘点：从 3 锚点的 ±14.9pp 到 n=9 的 **±8.8pp**，已吃掉到 n=20 可得降幅的约 ⅔；
> 8→9 边际仅 −0.37pp，9→12 再降 1.4pp，12 之后每步 <0.3pp（明显递减）。
> **结论：N=9（±8.8pp）是成本/判别力的合理平衡 —— 实测支持沿用 N=9 默认**；
> 对高精度/高风险租户可选 N=12（±7.4pp），N>16 不划算。（绝对 soft 0.52 仅反映当前模板水平，
> 与 N 无关；定 N 看的是方差结构。）

### 1.4 切分策略（少样本对策）

- **滚动留一 / k-fold**：12–15 张时不固定 3=train，而是滚动留出 1–几张做 val，降低单一切分的偶然性；
- **anchor 必入 train**：3 张客户精选样本始终在 train，保证技能先满足客户底线；
- **全局技能的"真留出"在 golden_set**：私有层 Gate 用客户的 N 噪声；**晋级全局库时**改用该国
  golden_set（几十张、零容忍）把关，把"过拟合单客户样本"的风险隔离在私有层（见 ADR P4）。

## 二、Japan-inv 测试策略（开发前后）

### 2.1 为什么 Japan-inv 是理想基准

- **现成 ML 划分**：363 对标注，`train 182 / val 73 / test 108`（seed=42 可复现）+ `init 8`（冒烟）。
- **字段名与平台 canonical 100% 对齐**（含 docType/invoiceNumber/invoiceDate/totalNetAmount/
  totalAmount/totalTaxAmount/currency/billFromName/billFromTaxIdentificationNumber/行项目/税额汇总）→ GT
  可**1:1 直接喂现有评分器**（`evaluator.compare` / golden 零容忍评分），无需映射层。
- **量足**：足以构造「训练上得分 vs 测试上得分」的泛化裂隙，这正是本次重构要打的靶。

### 2.2 角色分配（与产品流对应）

| Japan-inv 划分 | 测试中的角色 |
|---|---|
| `train` 抽 3 + N | 模拟客户的 anchor + 噪声样本（迭代输入） |
| `val`（73 抽样） | Gate 的 held-out 验证集（模拟客户噪声样本的"放大版"） |
| `test`（108，**全程不参与迭代**） | **最终泛化裁判**：开发前后只在这里比分 |

> test 是"圣杯"：迭代/调参/Gate 全程**绝不触碰** test，只在开发前后各跑一次，量"真泛化"。

### 2.3 黄金度量：开发前后必须对比的三个数

1. **测试集字段级精度**（test 108 上）：重构**后** ≥ **前**（核心收益：泛化提升）。
2. **训练-测试裂隙**（train_acc − test_acc）：重构**后** < **前**（核心假设：Gate 收窄过拟合）。
3. **每轮 LLM 调用数 / 墙钟**：重构后**不超预算**（新增 Aggregate/Clip/Gate 阶段，靠并发+早退+反思缓存摊薄）。

**做法**：动代码前先跑一次 **Baseline 快照**（当前系统在该 harness 上的上述三数）→ 这就是"要打败的数字"。

### 2.4 测试用例编排（巧妙之处）

**A. 中心假设测试 — Gate 收窄过拟合**
- 构造"易过拟合"场景：train 仅 3 张精选干净样本迭代。
- 量 OLD vs NEW 的「train_acc 高、test_acc 低」裂隙；NEW 必须**收窄裂隙**且 **test_acc 不降反升**。

**B. 噪声量扫描（定 N 的实证）**
- 训练样本 k ∈ {3,5,8,12,16,24}（3 anchor + (k−3) 从 train 随机噪声，seed 固定）。
- 对每个 k 测 val + test 精度，画曲线找**肘点** → 产品 N 阈值由此设定（替换 §1.3 的初值）。

**C. 逐机制行为测试（P1 各件）**
- **Gate**：人造一条 edit —— 在 train 上↑、在 val 上↓ —— 必须被**拒**并入 rejected buffer。
- **编辑预算/Clip**：一轮产出 edit 数 ≤ L；断言**不再整段重写** prompt（diff 行数受限）。
- **缺陷 vs 失误**：注入"1/N 偶发错"→ 判 `EXECUTION_LAPSE`（只进附录、正文字节不变）；
  "k/N 系统性错"→ 判 `SKILL_DEFECT`（改正文）。
- **被拒缓冲**：上一轮被拒的 edit，下一轮 reflect/clip **不再提**。
- **聚合支持度**：3 张同错 → 该 edit `support_count=3`；1 张错 → `support_count=1`。

**D. 回归护栏（必须不破）**
- MY/JP **golden_set 跑分不降**（用已提交的 `eval/golden_set/*`）。
- **country-lock** 字段仍被排除反思 + 钉死国家 spec（invoiceNumber/invoiceDate/billFromName/
  billFromTaxIdentificationNumber 在迭代后不变）。
- **单调 finalize**：最终版 ≥ 起始版（既有不变式）。

**E. 成本/时延预算**：单轮 LLM 调用数与墙钟在阈值内（CI 里设硬上限，超了红）。

### 2.5 harness 落点（开发期工具，不入生产路径）
- `backend/app/ocr_optimizer/eval/bench_japan_inv.py`：读 Japan-inv 划分 → 跑平台抽取 → 调
  `evaluator.compare` 算字段级精度 → 输出 train/val/test 三数 + 裂隙 + 调用数；可被 pytest 与 CLI 复用。
- 复用现有 golden 评分逻辑，不另造轮子。结果落 `ckpt/bench/<git-sha>.json` 便于前后对比。

## 四、已定决策（2026-06-26）
1. **噪声样本量**：**N = 9**（总确认 12 张）。最低强制 N=7（总 10）。**§2.4-B 噪声扫描已实测确认 N=9**（±8.8pp，合理平衡；高精度可选 N=12）。

## 五、测试成本与采样策略（token 预算）

> 回应"val 73 / test 108 是否每轮全量、会不会烧太多 token"。**核心：两个循环要分清，且基准不全量、不每轮。**

### 5.1 两个循环互不相同（关键澄清）

| | 产品迭代循环（每个客户 API） | 开发基准（Japan-inv） |
|---|---|---|
| 用谁的样本 | 客户自己的 **12 张**（3 anchor + 9 噪声） | Japan-inv 划分 |
| Gate 的 val | 这 12 张里**滚动留一抽出的 ~1–4 张** | train 抽 12 模拟客户；val 用其中留一 |
| 是否碰 73/108 | **完全不碰** | 仅开发期、少数几次 |
| 触发频率 | 客户每次迭代 | **我们手动跑几次**（非持续） |

### 5.2 产品 Gate ≈ 零额外 token（重要）

当前 `run_orchestrator` 每轮 step-1 **本来就把全部样本 OCR 一遍**（`run_ocr_on_samples`）再逐字段评估。
留出 Gate **不新增 OCR**——只是把已 OCR 的 12 张里 ~4 张**划为 val**（不参与 optimize，只用于 accept/reject）。
候选技能在 val 上的验证可**复用下一轮 step-1 的 OCR**。→ **Gate 在产品里几乎不花额外 token。**

### 5.3 Japan-inv 基准：不全量、不每轮

- **test(108) = 期末考**：只在**阶段边界各跑一次**（Baseline 1 次、P1 后 1 次、P2 后 1 次…），**绝不每轮、绝不进内循环**。
- **内循环 Gate** 用小 val 子集（滚动留一 ~4 张），**不是 73**。
- **val(73) 全量**：很少用；仅偶尔做"验证器自身高保真校验"时抽 ~15。
- **噪声扫描（§2.4-B）**：6 个 k 点，每点 1 次模拟迭代 + test 评分；扫描期 test 用**缩减子集 ~50** 找肘点，
  **选定 N 后才在全量 test 108 确认 1 次**。

### 5.4 总量化（整个 P0'→P2 开发期，单位＝OCR 调用次数）

| 用途 | OCR 调用 |
|---|---|
| Baseline test 全量 | 108 |
| 噪声扫描（6×(12样本×3轮 + test子集50)，re-OCR 可缓存，保守） | ~500–700 |
| 选定 N 后全量 test 确认 | 108 |
| P1 后 test 全量 + 机制测试 | ~150 |
| P2 后 test 全量 | ~120 |
| **合计** | **≈ 1,000–1,200 次**（分散在数次手动触发，非持续） |

按 qwen3-vl-plus 单次 ~8–10K token 估算，整个开发期 ≈ 1,000–1,200 次 ≈ **1,000–1,500 万 token**，
按 DashScope qwen-vl 价位约**几十元人民币量级**——可控、且**只在开发期一次性**，生产路径零负担。

### 5.5 省 token 的工程手段
- **OCR 结果缓存** `key=(sample_hash, skill_version_hash)`：回归重跑基准（改代码、技能轨迹不变）大量命中；复用平台已有 golden 评测缓存。
- **阶段边界才跑全量 test**，内循环只跑小 val 子集；扫描用缩减 test，定 N 再全量确认 1 次。
- **并发**（已调）+ **"0 未达标字段即早退"** 跳过整轮 OCR。
- temperature=0 让同 (sample, skill) 的 OCR 近确定 → 缓存有效。
