# 实验 · JP 模板 schema 传/不传 A/B —— 决定开关默认值的关键证据

> 日期：2026-08-28 ｜ 分支 `feat/schema-passed-to-model`
> 脚本：`backend/eval_samples/schema_ab/jp_schema_ab.py`
> 模型：gemini-3.5-flash · temperature=0 · seed=42（与线上同参）

## 1. 为什么 JP 是关键验证对象

`japan/JP_invoice_receipt.yaml`（id `jp-v8`）的设计与 MY 相反 ——
它的 remark 明写「**删除正文与 schema 的重复表述**」：

| | 正文 | schema description |
|---|---|---|
| MY 7_13 | 18.9k 字符（规则主要在这） | 有，且与正文**有意冗余** |
| **JP jp-v8** | **1.76k 字符**（只有切分/计数/通用约束） | **2.54k 字符，26 个字段的识别规则几乎全在这** |

也就是说：**schema 不下发时，JP 的绝大部分字段规则是死字**。
这正是「开关是否该默认打开」最需要的对照实验。

## 2. 数据与打分

复用 `japan/` 现成基建，不自造：
- 原件 `japan/docs/`（115 份）、GT `japan/result/`、`japan/split.json` 的 dev/test/val 三分；
- 打分器 `japan/_bench/score_jp.py`（字段级准确率：只考 GT 有值字段，
  漏检实体全字段计 0，明细数组逐行匹配；口径此前已确认）。

## 3. 结果

### dev split（12 份）

| arm | 字段准确率 | 耗时/份 | 输入 token | 输出 token | 漏检 | 误检 |
|---|---|---|---|---|---|---|
| 不传 schema | 0.1876 | 3.8s | 2,135 | 526 | 7 | 4 |
| 传 schema | **0.5385** | 4.3s | 2,135 | 859 | 3 | 3 |

**+0.3508（+187%）**

### test split（10 份，held-out — 排除「只在 dev 上好」）

| arm | 字段准确率 | 耗时/份 | 输入 token | 输出 token | 漏检 | 误检 |
|---|---|---|---|---|---|---|
| 不传 schema | 0.3972 | 5.4s | 2,418 | 895 | 3 | 12 |
| 传 schema | **0.7945** | 9.0s | 2,418 | 2,082 | 2 | 7 |

**+0.3972（+100%）**，且 **9/9 有效样本全部提升，无一例外**：

### 三个附带发现

1. **输入 token 完全相同**（2,135 / 2,418 两模式逐份一致）。
   `response_schema` 走 API 的结构化输出通道，**不计入 prompt token** ——
   传 schema 在输入侧是**零成本**的。
2. **代价在输出侧与耗时**：输出 token 涨 63%–133%、耗时 +0.5s(dev) / +3.5s(test)。
   原因是提取出的字段变多了（这正是准确率提升的来源），不是白烧。
3. **不传 schema 会产出非法类型**：test split 有 1 份把 `page` 输出成
   `int` 而非数组，直接让打分器 `TypeError` 崩溃。传 schema 时 0 份违规。
   下游解析器遇到这种输出同样会炸 —— 硬约束防的正是这件事。

## 4. 结论：开关应当默认打开

**我此前（v6.1 实验报告 §3.3）建议默认保持 `False`，理由是「JP 未验证」。
该前提现已消除，结论随之更正为：`PASS_SCHEMA_TO_MODEL` 应默认 `True`。**

汇总两个国家模板的全部证据：

| 模板 | 规则承载方式 | 传 schema 的效果 |
|---|---|---|
| MY 7_13 | 正文为主 + description 冗余 | 持平或略优（Phase 2 三样本 18/18 开=关；Phase 3 黄金集 4 seed 开≥关，一次 +15.6pp）|
| JP jp-v8 | **description 为主** | **+100%～+187%**，9/9 样本全升 |

- 成本：输入 token **零增加**；输出 token 与耗时上升，但来自「真的多提取了字段」。
- 风险：三次观察到的「开启后变差」根因**全部**是模板规则缺口
  （Tax Invoice 判据含糊、BRN 自检漏括号旧号、v6 的负号规则不足），
  修法都是改规则，且修完对关闭侧同样有益。
- 反向风险更大：**保持关闭 = JP 这类模板在生产里只发挥 1/3 的能力**，
  且随时可能吐出违反 schema 的非法类型。

### 仍需保留开关本身

默认值改 True 不等于删掉开关 —— 它仍是回退手段（`.env` 改一行重启）。
首次部署到生产时仍建议按 runbook 观察 24–48h（plan Phase 4）。

### 连带待办

`japan/JP_invoice_receipt.yaml` 的**文件名不符合加载器约定**
（`template_loader` 扫的是 `<COUNTRY>_invoice_prompt.yaml`，且在**仓库根**）。
当前 JP 模板不会被平台加载，`test_bench_harness.py` 的 2 条用例也因此长期红灯。
若要让 JP 进入平台流程，需放到仓库根并改名为 `JP_invoice_prompt.yaml`；
另外它的 `prompt_format` 缺 `# Part 1` 标记，loader 会 fallback 成
「整段作为 country_global_text」（本次实验直接读 yaml，未受影响）。
