# 设计与开发计划 · MY 模板分层瘦身（对照 JP 格式的取舍）

> 状态：R0/R1/P2/R2/**R3 完成**（模板现为 **7_15h**，§1.3 与 §1.34 已迁，
> 正文 13,998 → ~12,100 字符）；R4（§1.35+§1.36 字段部分）、R5（§1.2+收口）待执行。
> 日期：2026-08-28 ｜ 分支 `feat/schema-passed-to-model` 系列工作的后续
> 结论先行：**应该瘦身，但不应照搬 JP 格式** —— 做「分层瘦身」：
> 字段级细则迁去 description（单一事实源），文档级裁决必须留正文。
> 预期收益是**输入成本 −30%~40% 与维护性**，不是时延，也不是准确率。

## 2. 为什么「迁」是对的（本会话攒下的硬证据）

1. **description 在输入侧是免费的。** 实测 `response_schema` 不计入 prompt
   token（JP A/B 中两模式输入 token 逐份完全相同）。同一条规则放正文要花钱、
   放 description 不花钱——迁移直接省掉这 ~5.5k 字符的输入成本。
2. **description 现在真的生效且效果被验证过。** JP：+100%~187%；MY：Phase 2/3
   开≥关。规则放 description 不再是死字。
3. **双写会漂移。** §1.34 已经要求「改动请两处同步」——人工同步纪律迟早失守。
   单一事实源消除这类债。
4. **schema 一通已经连续暴露 3 处双写债**（Tax Invoice「等」字、BRN 括号旧号、
   v6 负号）——每一处都是「description 与正文各说各话」的产物。

## 3. 为什么「不能照搬 JP」（同样是硬证据）

1. **v6.1 实验直接否决了"删结构性复述"**：删掉 2,156 字符的「输出字段清单」
   （键名+类型+**enum 内联**）后准确率 51/54→48/54。response_schema 的 enum 只保证
   **输出值合法**，不提供**如何在候选间选择**的语义引导——composer 渲染的紧凑
   字段树（含 enum）必须留在正文。
2. **切分与分类裁决无处可去**：G 类段落（≈6,000 字符）是文档级/跨字段推理，
   schema 是字段级结构，承载不了它们。JP 正文留的恰恰也是这两类——
   所以正确说法是「MY 收敛到 JP 的**分层原则**」，不是「MY 压到 JP 的长度」。
3. **时延不会变好**：v6.1 实测输入 −17% 换来耗时 +0.5s——时延由输出 token
   与网络主导。「提升识别效率」的真实内涵是**输入成本与可维护性**，
   预先把预期摆正，避免拿时延验收。
4. **JP 的准确率不构成"瘦身更准"的证据**：两国样本集、GT 口径不同，0.79 vs MY
   的数字不可直接比。瘦身的准确率目标是**不降**（单调门），不是提升。

## 4. 两个前置门（不过门不动手）

**P0 · 生产开关已灰度稳定 —— 这是【部署门】不是【开发门】**（2026-08-28 修正）。
description-only 的规则在开关关闭时是死字，所以一次回退（.env 改 false）
就等于删掉 MY 39% 的规则。但该风险只在**生产**成立：
- **本地分支上 R2–R5 可以照做**（模板与代码同分支、原子部署，不影响线上）；
- **合并/部署前必须**：腾讯云灰度 `PASS_SCHEMA_TO_MODEL=true` 观察 24–48h
  （plan-schema-not-passed-to-model.md Phase 4），且部署后**不得**在未回滚
  模板的情况下单独把开关改回 false。
- 瘦身后的模板需在 remark 里标注「依赖 PASS_SCHEMA_TO_MODEL=true」，
  避免后人误操作。

**P1 · qwen 回退通道补文本渲染。** 这是**最硬的架构约束**：DashScope 视觉模型
不支持 response_schema，qwen 收到也忽略。当前 MY 在 qwen 上能跑好，正因为规则
在正文里；迁移后一旦主力熔断切到 qwen 备份，**迁走的规则全部消失**。
处置：在 processor 层做「按 provider 渲染」——provider 不支持结构化输出时，
把 schema description 自动渲染成文本附录拼进 instruction（qwen 付这笔 token，
Gemini 不付）。单一事实源仍在 schema，两个 provider 各取所需。
JP 模板在 qwen 部署上同样吃这个修复的红利。

### ⚠️ R2 失败给出的关键结论（影响后续全部轮次）

**「静态逐句同款」≠「可安全删除」。** 正文段落不只是规则容器 —— 删掉它会
扰动模型对整份任务的处理，副作用落在**与该段无关的字段**上。这与 v6.1 实验
（删「输出字段清单」→ 准确率 51/54→48/54）是同一现象的第二次出现。

**当前的门本身样本量不足。** `sample_batch` 每批硬上限 5 个样本，一份文档翻转
即 ±0.20 —— 判别力太粗，既可能误杀（把抖动当退化）也可能漏放。R2 的下降虽已
用同窗口复跑排除抖动，但「1 份文档」的因果仍不够扎实。

**后续轮次的前提条件（新增 P2）**：在继续 R3–R5 之前，必须先把评测判别力提上去：
- 扩大黄金批次（解除 `size=min(size,5)` 硬上限，或改为多批次聚合 ≥20 样本）；
- 或引入「逐样本配对比较」（同一份文档在两版模板下的得分差），而不是只看批次均值；
- 否则每一轮都会陷入「降了 0.15 但说不清是模板还是那一份样本」的困境。

**回退**：`git checkout HEAD -- MY_invoice_prompt.yaml`，模板已回到 7_13，
本地 DB 已刷新（`prompt_refreshed: True`）。R2 未提交任何模板改动。

#### 第六课（S3 收口新增）
6. **desc 之间存在二阶交互，且受 schema 字段顺序调制**——两处各自无害的
   description 改动组合后掐断了跨字段推断链（net 先于 total 生成，取值锚点
   相互传染）。单字段消融不够，收口前必须做组合门（全池配对天然覆盖）；
   涉及金额链（net/total/tax）的 desc 改动要显式写符号与依赖方向。

#### 提示词精确性五课（本轮实证，非理论）
1. **否定式禁令会诱发被禁行为**——「严禁拆成两条同号记录」让模型拆成两条；
   规则要写成正向形式（「X 与 Y 是同一张票，合并」）。
2. **作用域即语义**——同一句「多处出现相互比对」在字段深层无害、提升为全局行
   即毒；把规则提升作用域前必须单行消融。
3. **压缩即语义风险**——「A / B / C」列举会被读成三选一，丢掉「并列时全保留」；
   压缩后必须逐句对照台账验语义等价。
4. **隐性 GT 惯例必须显式化**——从没写下的规则（无税 net=total）靠模型好心
   推断在撑着，正文一瘦身就塌。
5. **规则冲突要显式裁决**——两条各自正确的规则（标题不同=拆 / 同号=合）交叉处
   必须写明例外，否则裁决权交给了 prompt 其余部分的「体量配重」。
