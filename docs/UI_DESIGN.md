# ApiAnything UI 设计文档

> 版本：v2.0 | 日期：2026-04-03
> 技术栈：Next.js 14 (App Router) + TailwindCSS + shadcn/ui

---

## 一、设计哲学

**单页核心，弹窗辅助**：整个产品以「AI 识别预览」为唯一核心页面，上传文档、矫正字段、调整 API 格式、调试优化全部在同一页面内完成。模板选择、API 生成等辅助流程通过弹窗承载，用户无需跳转页面即可完成从上传到生成 API 的完整旅程。

**字段驱动，逆向定位**：不使用传统的「框选图像区域 → 提取内容」，而是「AI 提取字段内容 → 逆向定位到文档区域高亮」。用户关注的始终是结构化字段，文档预览只是辅助验证手段。

**Prompt 泛化，不存位置**：用户画框或移动识别框时触发的专项 OCR，其结果用于丰富 Prompt 和自动调优，系统只保留 Prompt 方法，不保留「通过坐标识别特定内容」的硬编码逻辑，确保识别能力可泛化到任意同类文档。

```
┌─────────────────────────────────────────────────────────────────────┐
│  ┌──────┐                                          [用量] [头像▾]  │
│  │ Logo │  工作台  API管理  设置                                     │
```

导航极简化，只保留三个入口：工作台（核心）、API 管理（查看已生成的 API）、设置。
模板市场、生成 API、沙箱调试等功能全部内嵌到工作台页面中，通过按钮+弹窗触达。

**路由结构**：

| 路径 | 页面 | 说明 |
|------|------|------|
| `/login` | 登录 | 邮箱+密码 / OAuth |
| `/register` | 注册 | 邮箱注册 + 组织创建 |
| `/workspace` | 工作台（核心页面） | 三栏布局，承载全部核心功能 |
| `/apis` | API 管理 | 已生成 API 的列表 + 详情 |
| `/apis/:id` | API 详情 | 调用统计 / Schema / 日志 / 文档 |
| `/settings` | 设置 | 账户 / 密钥 / 用量 / 团队 |

### 3.2 三栏详细设计

#### A 栏：文档预览区（55%）

**核心职责**：渲染文档原文 + 字段高亮叠加层 + 画框工具。

**文档渲染**：
- PDF：使用 PDF.js 渲染，支持缩放/翻页
- 图片（PNG/JPG）：直接渲染，支持缩放/平移
- Excel：表格预览（转 HTML 表格）

**字段高亮叠加层**（核心交互）：
- 在文档图像上方叠加一个 Canvas / SVG 图层
- 当用户在 B 栏 hover 某个字段时，A 栏自动高亮该字段对应的文档区域
- 高亮方式：半透明彩色矩形 + 字段名标签（如 `发票号码`、`行1:品名`）
- 不同字段组用不同颜色（基本信息=蓝色、货物明细=绿色、税额=橙色）
- 高亮区域通过「逆向定位」确定（见 3.4 节）

**工具栏**：
- 🔍+ / 🔍-：缩放
- ✋ 拖拽平移（默认模式）
- 📐 画框工具：用户在文档上框选区域 → 触发专项 OCR → 结果送入 B 栏（见 3.5 节）

#### B 栏：字段定义与矫正区（30%）

**核心职责**：展示和编辑 AI 提取的结构化字段，支持精细化的嵌套数据结构。

**字段展示结构**：采用分组卡片式设计，每个字段组是一个可折叠卡片。


**字段编辑能力**：

| 操作 | 方式 | 说明 |
|------|------|------|
| 修改值 | 直接点击字段值编辑 | 实时同步到 C 栏 JSON |
| 修改类型 | 点击类型标签切换 | string / number / date / boolean / array / object |
| 添加字段 | [+字段] 按钮或自然语言 | 支持手动和 AI 对话两种方式 |
| 删除字段 | 右滑或右键菜单 | 需确认 |
| 重命名 | 双击字段名 | 英文 key + 中文 label |
| 调整嵌套 | 拖拽或自然语言 | 字段提升/下沉到不同层级 |
| 数组管理 | [+行] 展开/折叠 | 添加/删除数组行 |
| 设置校验规则 | 校验规则卡片 | 数学关系、枚举约束、格式约束 |

**字段 ↔ 文档联动**：
- **hover 联动**：鼠标悬停 B 栏任一字段 → A 栏高亮对应区域
- **点击聚焦**：点击 B 栏字段 → A 栏自动滚动并放大到对应区域
- **数组行联动**：hover 货物明细的"行1" → A 栏高亮文档中整行货物信息

#### C 栏：API 结果预览（15%）

**核心职责**：实时展示 B 栏字段组合后的 API 输出 JSON + 验证状态 + 代码示例。

**内容**：
- API endpoint 信息（`POST /extract/{api_code}`）
- 实时 JSON 预览（随 B 栏编辑同步更新）
- Schema 验证状态（字段匹配、类型校验、业务规则校验）
- 多语言代码示例（Python / cURL / Node.js / Java）
- 历史版本切换（v1 / v2 / v3...）

**C 栏 ↔ B 栏联动**：
- hover C 栏 JSON 某个 key → B 栏对应字段高亮 + A 栏区域高亮
- C 栏 JSON 出现验证错误 → B 栏对应字段标红

### 3.4 逆向定位机制（字段 → 文档区域）

这是本系统区别于传统 OCR 工具的核心设计。

**原则**：不通过「在图上画框 → 提取框内内容」来定义字段，而是 AI 提取结构化内容后，逆向推断每个字段值在文档中的大致位置，用于高亮展示。

**实现流程**：

```
1. AI 处理器返回结构化 JSON
   → 同时返回每个字段的 location_hints（可选）

2. Schema Generator 补充位置信息
   → 对文档进行 OCR 获取全文 + 每个文字块的坐标
   → 用字段值在全文中做模糊匹配（fuzzy matching）
   → 匹配成功 → 记录 bounding_box {page, x, y, w, h}
   → 匹配失败（计算值等）→ 标记为 "derived"，不显示高亮

3. 前端渲染高亮
   → 在文档预览 Canvas 上叠加 SVG 矩形
   → 矩形颜色 = 字段组颜色，透明度 30%
   → 显示标签：字段中文名
```

**哪些字段有高亮，哪些没有**：

| 字段类型 | 高亮行为 | 说明 |
|---------|---------|------|
| 直接提取值（发票号、日期、名称） | ✅ 精确高亮 | 文档中有原文 |
| 数组行中的值（品名、数量、单价） | ✅ 行级高亮 | 高亮整行区域 |
| 计算值（合计、税额小计） | ⚠️ 最佳匹配 | 尝试匹配文档中的数字 |
| 衍生值（校验结果、聚合值） | ❌ 无高亮 | 标记 "derived" |

**位置信息不持久化到 Prompt**：位置坐标仅在当前会话的前端使用，不存入 PromptVersion，不影响 Prompt 泛化能力。

### 3.5 画框工具与专项 OCR（Prompt 自优化机制）

当 AI 自动提取的结果不准确时，用户可使用画框工具辅助矫正。

**交互流程**：

```
1. 用户点击 A 栏工具栏的 [📐 画框] 按钮，进入画框模式

2. 用户在文档上拖拽画出一个矩形框
   → 框选区域高亮，出现浮窗：
   ┌──────────────────────────┐
   │ 识别到的内容:             │
   │ "零件A M10×50 10 100 ..." │
   │                          │
   │ 这是哪个字段？            │
   │ ○ 新增为新字段            │
   │ ○ 矫正现有字段: [选择 ▾]  │
   │ ○ 作为辅助信息提供给 AI   │
   │                          │
   │ [确认]         [取消]     │
   └──────────────────────────┘

3. 用户选择操作：

   a) "新增为新字段"
      → 触发 correction engine：
        - 将 OCR 内容发送给 LLM
        - LLM 推断字段名、类型、在 Schema 中的位置
        - 更新 Prompt（增加提取该字段的指令）
        - 创建新 PromptVersion
      → B 栏新增字段，C 栏 JSON 更新

   b) "矫正现有字段"
      → 用户选择要矫正的字段（如 "行1:品名"）
      → 触发 correction engine：
        - 将「用户框选内容」+「当前字段值」+「原 Prompt」发送给 LLM
        - LLM 生成改进后的 Prompt 提取指令
        - 使用新 Prompt 重新处理文档
        - 创建新 PromptVersion
      → B 栏字段值更新，版本号递增

   c) "作为辅助信息"
      → OCR 内容作为额外上下文附加到对话中
      → 用户可在对话框进一步描述
```

**Prompt 自优化 (Auto-Research) 机制**：

```
用户框选矫正触发后：

Loop (max 3 轮):
  1. 生成/修改 Prompt
  2. 用修改后的 Prompt 重新处理文档
  3. 对比结果与用户期望
  4. 若结果满意 → 保存 PromptVersion，退出循环
  5. 若结果仍不满意 → LLM 自我反思，调整 Prompt 策略，继续

最终保存：
  - 仅保存最终的 Prompt 文本（PromptVersion）
  - 不保存框选坐标、位置信息、OCR 原文等
  - 确保 Prompt 可泛化到同类型的其他文档
```

**关键设计决策**：
- ✅ 保留的：Prompt 文本、Schema 定义、字段校验规则
- ❌ 不保留的：框选坐标、文档特定的位置信息、OCR 中间结果
- 这确保了一个在「发票A」上调好的 API，能正确处理「发票B」「发票C」

### 3.6 嵌套数据结构设计（精细化字段）

B 栏的字段编辑器需要支持复杂的嵌套结构，核心场景：

#### 场景一：货物明细（多行数组）

```json
{
  "items": [
    {
      "line_no": 1,
      "name": "A零件",
      "spec": "M10×50",
      "quantity": 10,
      "unit_price": 100.00,
      "amount": 1000.00,
      "tax_amount": 130.00
    },
    {
      "line_no": 2,
      "name": "B零件",
      "spec": "M12×60",
      "quantity": 5,
      "unit_price": 160.00,
      "amount": 800.00,
      "tax_amount": 104.00
    }
  ]
}
```

B 栏展示：卡片内每行可折叠，展开后显示子字段。

#### 场景二：税额汇总（数组 + 合计行）

```json
{
  "tax_details": [
    { "tax_type": "增值税", "tax_rate": "13%", "tax_amount": 234.00 }
  ],
  "tax_total": 234.00   // 🔗 = SUM(tax_details[*].tax_amount)
}
```

B 栏展示：数组下方有「合计」行，显示公式引用关系（🔗 图标）。

#### 场景三：数据逻辑加工规则

某些字段不是直接 OCR 提取，而是需要基于提取值进行逻辑计算。B 栏支持定义：

```
┌─ 📦 数据校验与加工规则 ──────────────────────┐
│                                              │
│  规则 1: amount = quantity × unit_price       │
│  规则 2: tax_total = SUM(tax_details.amount)  │
│  规则 3: grand_total = SUM(items.amount)      │
│                                    + tax_total│
│  规则 4: tax_rate 枚举: [3%, 6%, 9%, 13%]     │
│                                              │
│  容差: ±0.01 (浮点精度)                       │
│                                    [+ 添加规则]│
└──────────────────────────────────────────────┘
```

这些规则会：
1. 在 C 栏 API 结果中实时校验（显示 ✅ / ⚠️）
2. 写入 Prompt，让 AI 在提取时也做校验
3. 写入 ApiDefinition，公有云调用时自动校验

## 七、关键交互状态

### 文档处理状态机

```
上传中 (uploading) → 排队中 (queued) → 处理中 (processing) → 完成 (completed)
                                                              → 失败 (failed)
```

| 状态 | UI 表现 |
|------|---------|
| uploading | A 栏显示上传进度条 |

```ts
onClick = () => {
  if (documents.length < 3) {
    Modal.warn({
      title: "样本量过少",
```

### 10.2 左侧模块列表


底部固定一个 `[+ Skill] 模块` 按钮 —— 占位，点击 toast `Coming Soon`（§13）。

### 10.3 顶部 Version + Run 状态条

```
[v1(init)] [v2 round1] [v2.1 manual ✏] [v3 round2 ★active]      ← Version 切换
─────────────────────────────────────────────────────────────────
Run #abc1234 · paused_for_review · round 2/5 · [下一轮 ▶] [完成此次 Run] [放弃]
```

- **版本 chip 颜色编码**：
  - `init` 灰色
  - `round` 蓝色（产生于某一轮）
  - `manual_edit` 紫色，带 ✏ 图标
  - `★active` 角标 + 绿框
- **Run 状态条**：仅当当前 API 存在 `paused_for_review` 或 `running` 状态的 Run 时显示。`completed` / `aborted` 后该条隐藏，但 Versions 切换器仍可回看历史版本。
- **按钮：**
  - `[下一轮 ▶]`：调 `POST /runs/{id}/advance`，body `{use_version_id?: <当前选中版本 id>}`。**默认 use_version_id = 最近一个 manual_edit 版本 ?? 最近一轮 round next_version**
  - `[完成此次 Run]`：弹模态框让用户从 Run 演化链上所有版本中选一个 activate；调 `POST /runs/{id}/finalize`
  - `[放弃]`：二次确认后调 `POST /runs/{id}/abort`

### 10.4 右侧详情区 — 单模块 5 Phase

只展示**当前选中模块**在**当前选中版本对应的 Round**中的数据。版本切换或模块切换都触发右侧重渲染。

Phase 4 旁有 `[✏ 编辑]` 按钮（详见 §10.6 编辑流），Phase 5 不可编辑（ocr_prompt 由 description+suggestions 派生）。

#### 数据映射（同 v1，保留不变）

| Phase | UI 名 | 数据源 |
|---|---|---|
| 1 | OCR 输出 | `Round.ocr_raw_outputs[sample]` 按 `module.json_path` 切片后展示 |
| 2 | 模块差异分析 | `Iteration.aggregate_diff` + `per_sample_results` |
| 3 | 分析原因 | `Iteration.optimization_suggestion` |
| 4 | 生成优化建议 | `Iteration.new_ocr_suggestions` + `new_description` |
| 5 | 生成新 Prompt | `Iteration.new_ocr_prompt` + 下一版本 `composed_prompt` |

#### Skills 子区（read-only）

固定在 5 phases 下方：
- 列出当前模块 `skill_ids` 对应 skill 卡片（MVP 阶段空列表）
- 展示 `Iteration.skill_feedback`（optimizer 关于 skill 的反馈文本，灰色斜体）
- `[+ 添加 Skill]` 按钮 → toast `Coming Soon`

### 10.5 版本切换器交互细节

数据加载策略：
- 进入 tab 拉一次 `GET /ocr-optimizer/versions`（含 origin / produced_in_round / overall_accuracy 摘要）
- 切换版本时按需拉 `GET /versions/{id}`（modules 全文）
- 若版本是 round 产物：再拉 `GET /runs/{runId}/rounds/{n}`（iterations + raw_outputs）
- 若版本是 manual_edit 产物：右侧 5 phases **沿用 parent_version 对应 round 的数据**，但 Phase 4/5 字段值显示 manual patch 后的版本，让用户直观看到"编辑前 vs 编辑后"
- 客户端 LRU 缓存

### 10.6 编辑流（manual_patch）

用户在 Phase 4 点 `[✏ 编辑]`：

1. 该模块的 `description` 和 `ocr_suggestions` 区域切到 inline 编辑模式（Textarea + JSON 编辑器）
2. 编辑期间，**顶部右侧出现一个 `[保存 patch → 生成 vX.Y]` 按钮**（绿色），左侧顶部出现 dirty 标志
3. 可以在多个模块上连续编辑，dirty 标志累加（"3 个模块有未保存改动"）
4. 点 `[保存 patch]`：
   - 调 `POST /versions/{currentVersion.id}/manual-patch` body `{edits: [{module_key, description?, ocr_suggestions?}, ...]}`
   - 后端返回新版本（status=draft, origin='manual_edit'）
   - 前端在 Versions 列表中**追加紫色 v2.1 chip 并自动选中它**
5. 之后用户可以：
   - 点 `[下一轮]` —— 后端用 v2.1 作为起点跑 Round (n+1)
   - 继续在 v2.1 上再编辑 → 生成 v2.2
   - 点 `[完成此次 Run]` 选 v2.1 → activate

**严格限制**：编辑面板**没有** ocr_prompt / skill_ids 的编辑入口（即使 hack 调用 API 也会被后端拒绝）。

### 10.7 触发流程端到端时序（Run 状态机）

```
用户点「开始优化」（顶部按钮，§见 WorkspaceHeader）
    │
    ▼ 前端校验：documents.length ≥ 3
    │

    │

    │        round: <Round1 详情> }
    │
    ▼ 前端：
    │   1. 刷新 Versions 列表（init + round1 产物 v2 出现）
    │   2. 默认选中 v2（新轮产物）
    │   3. 默认选中第一个 module（按 accuracy 升序，最差的最先看）
    │   4. Run 状态条出现 "paused_for_review · round 1/5"
    │
    ▼  用户 review 模块详情
    │   │
    │   ├─ 用户编辑 suggestions → 点 [保存 patch] → 生成 v2.1（紫）
    │   │     │
    │   │     └─ 用户继续 review / 编辑 / 直到满意
    │   │

    │   │     │

    │   │     │

    │   │
    │   └─ 用户点 [完成此次 Run]
```

### 10.8 与「字段视图 / 校验规则 / 统计分析」的关系

- **字段视图**：展示**当前 active 版本**的字段结构；optimize 进行时不阻塞用户继续标注
- **校验规则**：不变
- **统计分析**：可叠加 Run 时间线 + 每轮 accuracy 折线
- **优化过程**：本章

- **Skill 子系统正式启用**（§13）：解锁 [+ Skill] 按钮真实功能

### 12.3 Tab B — 上传已标注数据（新）

```
┌─────────────────────────────────────────────────────┐
│  上传图片或 PDF 文件 (1)                              │
│  ┌─────────────────────────────────────────────┐    │
│  │  📎 receipt_001.png  · 1.2 MB    [移除 ✕]  │    │  ← 已选状态
│  │  [点击重新选择]                              │    │
│  └─────────────────────────────────────────────┘    │

│  上传标注 JSON 文件 (2)                               │
│  ┌─────────────────────────────────────────────┐    │

└─────────────────────────────────────────────────────┘
```

- 两个文件选择器都用单文件 picker；**不允许选文件夹**
- 文件 (2) 上传后**前端立即解析**做 lint：JSON 合法 + 含 `annotations[]` + 每项有 `field_path` 和 `value`
- 两个文件**都选完才能点 `[上传 & 创建]`**
- 上传后调 `POST /api/v1/documents/upload-with-annotations` (multipart: `file` + `annotations`)

### 12.4 JSON 格式（包装元信息版）

```json
{
  "filename": "receipt_001.png",
  "annotations": [
    {"field_path": "store_name", "value": "全家便利店"},
    {"field_path": "date", "value": "2026-03-12"},
    {"field_path": "items[0].name", "value": "矿泉水"},
    {"field_path": "items[0].price", "value": 3.50},
    {"field_path": "items[0].quantity", "value": 2},
    {"field_path": "items[1].name", "value": "三明治"},
    {"field_path": "items[1].price", "value": 12.00},
    {"field_path": "total", "value": 19.00}
  ]
}
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `filename` | 否 | 仅作 sanity check 与文件 (1) 文件名比对；不一致警告但允许提交 |
| `annotations` | 是 | array，至少 1 项 |
| `annotations[].field_path` | 是 | JSONPath-lite：`a.b.c` / `a[0].b`。后端校验是否命中 response_schema leaf path |
| `annotations[].value` | 是 | 标注值；后端按 schema 校验类型 |

### 12.5 错误处理

- 客户端 lint 失败：红色提示框列出第一个错误，不让上传
- 后端 422（field_path 不命中 / 类型不匹配）：上传后 toast 错误 + 详情列表
- 后端 5xx：toast + 保留已选文件让用户重试

### 12.6 与现有上传逻辑的关系

- 不替换 Tab A，并存
- 后端 `upload-with-annotations` 内部走 `upload_document()` + 一段事务内的 annotation 批量写入；用同样的 storage backend
- 上传成功后行为与 Tab A 一致：进入 `/workspace/api/{newApiDefId}`，新文档自动成为 sample 集合第一项，且**所有 annotations 已是 GT**（`source='manual', is_corrected=True`）—— 用户可立即继续添加更多样本，无需手动标注这一张

### 13.5 严格限制（与后端 §15 一致）

- Optimizer **永远不能** 修改 `OcrModule.skill_ids` —— 后端 Pydantic 校验拒绝
- 用户手动 patch（§10.6 编辑流）**也不能** 修改 `skill_ids` —— `/manual-patch` 端点的 edits schema 不含此字段
- 未来 skill 子系统上线后，修改 skill 的唯一合法途径是 `/ocr-skills/...` 和 `/modules/{key}/skills` 专用端点
