# 日本 Invoice/Receipt 专用 Prompt 优化报告

**结论先行：目标 96% 未达成。** 定稿版 v8 单次调用 —— 开发集 **62.9%**、验证集 51.6%
（dev+val 合计 56.7%，与 v3 完整版的 57.3% 在噪声内等价，但 token 少 45%，见 §3.07）；
**多次调用取并集可到验证集 58.7%**（见 §3.06）。
相比出发点的全球通用模板（开发集 37.0%）提升 **+24.8pp**（相对提升 67%），但距 96% 仍差约 38pp。

**两个关键的方法论发现**（都改变了对结果的解读）：
1. **运行间噪声 1.77pp**——同一 prompt 跑两次，准确率相差 1.77pp、漏检实体相差 7 条。
   这意味着多数 prompt 变体之间的差距落在噪声内，单次运行的排名不可靠（§3.0）。
2. **多次运行取并集是唯一被验证有效的提升**——val +4.3pp、漏检 9~13 → 5，在 held-out 集上复现（§3.06）。

瓶颈不在 prompt 措辞，在 qwen3-vl-plus 对日文票面的识别稳定性与精度（详见第四节归因）。

### 2.9 ✅ v8 定稿版：体积压缩 45%，精度持平

把已验证有效的规则合并成精简版（`JP_invoice_receipt.yaml` = v8）：v3 骨架 + v6 的
「但し書き不得吞掉明细表」+ taxCategory 用票面原词 + billToName 剥敬称（GT 统计证实），
并删除正文与 schema description 之间的重复表述（同一规则只写一处）。

**字段结构与 v3 完全一致**（脚本比对 schema 的字段名/类型/枚举，忽略 description → 全等）。

| | v3 | v8 |
|---|---|---|
| prompt 正文 | 6650 字符 | **1760 字符**（−74%） |
| schema | 7205 字符 | 5908 字符（−18%） |
| **合计** | 13855 字符 | **7668 字符（−45%）** |
| dev 准确率 | 61.76% (漏检 9 / 误检 32) | **62.91%** (漏检 10 / 误检 40) |
| val 准确率 | 53.55% (漏检 11 / 误检 15) | 51.63% (漏检 **7** / 误检 21) |
| dev+val 合计 | 57.27% | 56.74%（−0.52pp） |

两集方向相反（dev +1.15pp / val −1.92pp）、幅度都在 1.77pp 噪声基线附近，合计差 0.52pp
→ **判定为精度持平**。另在同一批 10 个抽样文件上单独对比，两版总分完全相同（342/620）。

v3 完整版保留为 `JP_invoice_receipt_v3_verbose.yaml`（规则表述更详尽，便于后续人工修订时查阅）。

### 3.0 ⚠️ 运行间噪声基线：1.77pp —— 前述变体排名不可靠

用**完全相同的 v3 prompt、相同模型、temperature=0** 重跑一次 dev：

| 运行 | 准确率 | 漏检实体 | 误检实体 |
|---|---|---|---|
| v3 第 1 次 | 61.76% (801/1297) | 9 | 32 |
| v3 第 2 次（同一 prompt） | **59.98%** (778/1297) | **16** | **41** |

**同一 prompt 两次运行相差 1.77pp，漏检实体差 7 条。** qwen 视觉模型即便 temperature=0 也不是
确定性的，而混贴页的实体切分对微小扰动极其敏感——一条实体没切出来，它的 7–10 个字段一起归零。

**这个噪声基线改写了上表的解读**：v3（61.8%）、v5（60.8%）、v6（61.5%）、v4（59.4%）之间
0.3–2.3pp 的差距**大部分落在噪声内**，不能据此断言某一版更优。「加规则改善一处、损失另一处」的
现象，有相当部分其实是运行间抖动。可靠的变体比较需要每版跑 3 次取平均——本次未做（成本 3 倍）。

### 3.05 prompt 语言实验：英文指令 + 日文术语（无提升）

把 v3 的规则**逐条原样翻译成英文**（票面术语、示例值全部保留日文原文），只改语言不改规则：

| 变体 | dev 准确率 | 漏检 | 误检 |
|---|---|---|---|
| 中文指令（v3） | 61.76% | 9 | 32 |
| 英文指令 + 日文术语（v7） | **61.84%** | 12 | 31 |

**差异 0.08pp（1 个字段），远小于 1.77pp 的噪声基线 → 语言不是影响因素。**

分项上有一个看起来成系统的规律（但同样需在噪声下打折）：英文版在**字符串取值口径**类字段更好
（billToName +12.1pp、登録番号 +5.5pp、invoiceNumber +4.9pp、billFromName +2.9pp），
中文版在**实体切分与分类**类更好（税汇总 −4.1pp、docType −2.7pp、currency −2.7pp）。
若要利用这一点，需先用多次运行确认它不是抖动。

### 3.06 ✅ 多次运行取并集：目前唯一真实有效的提升（val +4.3pp）

既然噪声实验证明模型对混贴页的切分是「抖」的而非「盲」的（同一张票在某次运行里能被看见），
就把多次运行的实体取并集：按（billFromName, invoiceDate, totalAmount）三元组去重，
同一条保留字段更全的那份（`_bench/merge_runs.py`）。**不需要新的 prompt，只需重复调用。**

**验证集（held-out）结果：**

| 方案 | 准确率 | 漏检实体 | 误检实体 | 成本 |
|---|---|---|---|---|
| 中文 v3 单次 | 53.55% | 11 | 15 | 1× |
| 英文 v7 单次 | 52.33% | 9 | 29 | 1× |
| v6 单次 | 51.95% | 13 | 20 | 1× |
| **3 次并集（v3+v7+v6）** | **57.83%** | **5** | 37 | 3× |
| 3 次投票（≥2 票才保留） | 53.93% | 15 | **10** | 3× |

开发集同样成立：单次最好 61.84% → **3 次并集 64.76%**，漏检 9~16 → **5**。

两项提升（dev +2.9pp、val +4.3pp）都**超出 1.77pp 的噪声基线**，且在 held-out 集上复现，是真实收益。
机理明确：漏检一条实体等于它的 7–10 个字段一起归零，并集把漏检从 9~16 条压到 5 条。

**取舍**：并集把误检从 15~29 抬到 37。当前打分口径下误检不进分母，所以准确率只升不降；
但生产环境里多余记录是有害的，若在意可改用投票模式（误检降到 10，代价是准确率回落到 53.93%）。
成本是 3 倍 token。

### 3.07 ✅ v8 精简合并版（定稿）：体积减半，精度等价

把各版**已被数据验证**的修正合并成一版，并删除「正文写一遍、schema description 再写一遍」的重复
（同一规则只保留一处）。合并内容：v3 骨架 + v6 的「但し書き不得吞掉逐行明细表」+ v5/v6 的
「taxCategory 必须用票面原词」+ GT 统计证实的「billToName 剥离末尾敬语」。

| | v3 完整版 | **v8 精简版** |
|---|---|---|
| prompt 正文 | 6650 字符 | **1760 字符** |
| schema | 7205 字符 | **5908 字符** |
| 合计 | 13855 | **7668（−45%）** |
| 字段结构 | — | **与 v3 完全一致**（脚本逐字段比对通过） |
| dev 准确率 | 61.76% | **62.91%** |
| val 准确率 | 53.55% | 51.63% |

**合计差 0.53pp（15 个字段），远小于 1.77pp 的运行噪声 → 精度等价**，而 token 用量减少 45%、

作为并集成员也有贡献：val 4 次并集（v3+v7+v6+v8）达 **58.72%**，漏检 5、优于 3 次并集的 57.83%。

### 3.1 两个非 prompt 维度的实验（均无效，已排除）

**渲染分辨率**：把 PDF 渲染从 150 DPI 提到 300 DPI（假设日文小票字号小、分辨率不足限制了字符识别）
→ dev **58.4%**，反而**低于** 150 DPI 的 61.5%。图像变大后 token 占用上升、长文档更易失焦。已排除。

**换模型（Gemini 2.5 Flash）**：在同一份 v3 prompt、同一批 9 个 dev 文件上做头对头对照——

| 指标 | qwen3-vl-plus | gemini-2.5-flash |
|---|---|---|
| 字段准确率 | 54.97% (315/573) | **57.59% (330/573)** |
| 漏检实体 | 7 | **4** |
| 误检实体 | 27 | **4** |
| 耗时 | 数百秒 | 88 秒 |

Gemini 的**实体检出是质变**（`20250619.pdf` 这个 47 页装订件，qwen3 误切成 21 条，Gemini 正确输出 1 条），
但**字段准确率只高 2.6pp**——说明瓶颈不只是模型，GT 口径与明细标注噪声是共同瓶颈。

**但 Gemini 在本机网络下不可用**：全量 dev 跑两次（4 并发、2 并发），分别有 29/44 和 21/44 个文件
因 `SSL: UNEXPECTED_EOF_WHILE_READING` 失败，成功率约 52%。这印证了项目 `CLAUDE.md` 记载的
「大陆云实例无法访问 Google Gemini，改用阿里云 DashScope」的既有判断。

**后续复测时网络已完全阻断**：尝试在 10 个抽样文件上对比 v3 与 v8 的 Gemini 表现时，10/10 全部
SSL 失败；单独发 5 次最小文本请求（无图片）也是 0/5 成功 → 不是并发或负载问题，是网络层阻断。

**收敛信号**：v3→v5 三次尝试，每次都是「改善一处、损失另一处」，总分锁在 59–62%。

## 四、最终成绩与失分归因

### 4.1 三分成绩（剔除冲突标注口径）

**v8 定稿版**（单次调用）：

| 集合 | 总准确率 | 实体 GT/匹配/漏检/误检 |
|---|---|---|
| dev | **62.9%** (816/1297) | 113 / 103 / 10 / 40 |
| val | **51.6%** (808/1565) | 77 / 70 / 7 / 21 |
| dev+val 合计 | **56.7%** (1624/2862) | 190 / 173 / 17 / 61 |

**v3 完整版**（同口径对照，含 test）：

| 集合 | 总准确率 | 标量字段 | 明细数组 | 实体 GT/匹配/漏检/误检 |
|---|---|---|---|---|
| dev | 61.8% | 70.9% (598/844) | 44.8% (203/453) | 113 / 104 / 9 / 32 |
| test | 59.3% | 66.4% (633/953) | 35.8% (119/333) | 128 / 106 / 22 / 12 |
| val | 53.6% | 65.0% (430/661) | 43.3% (391/904) | 77 / 66 / 11 / 15 |

各集合表现一致（52–63%），**无过拟合**。val 偏低的原因是它的明细字段占比最高（904/1565 = 58%，
含 61 张小票的 `000005.pdf`），而明细恰是最难的部分。

### 4.2 失分归因（按可修复性分三类）

**① 模型 OCR 精度不足 —— prompt 改不动（占失分主体）**

qwen3-vl-plus 在日文感热纸小票上的字符识别错误是硬伤，实测样例：

| 类型 | GT | 模型输出 |
|---|---|---|
| 假名字符错 | `ハイセンスジャパン株式会社` | `ハイスンジャパン株式会社` |
| 整段乱码 | `株式会社スペースゼロ` | `みんなどの「イザ」アフターート和歌伯大町店` |
| 税号位数丢失 | `T4010001137274`（13位） | `T401000113724`（12位） |
| 金额小数点 | `1181.82` | `11818` |
| 混贴票据幻觉 | 6 张小票 | 输出 20 条（票号逐一递增、日期逐日递减、金额恒定的外推序列） |
| 竖排/旋转票漏检 | 竖排「領収証 金11,270円」 | 完全跳过 |

**这类错误有杠杆效应**：金额和商家名同时读错 → 实体对齐失败 → 该实体全部 7–10 个字段计 0。
`5806.jpg` 的 3 张出租车票就是这样从「字段错」升级成「整条漏检」。

**② GT 标注本身不可信 —— 已客观剔除，但仍有残留**

11 组重复原件中 **10 组的两份标注互相冲突**（同一张图人工标两次，结果不同）。这是标注口径不确定的
硬证据，已生成 `gt_exclusions.json` 剔除 446 项冲突字段。但剔除后总分只提升 **+0.87pp**
（60.89% → 61.76%）——说明**GT 噪声不是主瓶颈**，剔除冲突字段时分子分母同时缩小。

冲突样例（同一张原件的两份 GT）：
- `Seria` + 地址`和光市駅前店` **vs** `Seria 川崎ルフロン店`（店名归属完全反向）
- 同一张票 `totalAmount` 标成 `2200` **vs** `200`
- `2025061701_2.pdf` 标 4 条实体 **vs** `2025061801.pdf` 标 46 条实体（同一张原件）
- 一份把 `駐車料金`+`B料金` 拆成 name+description，另一份合并成 `駐車料金 B料金`

另有三个错因分析 agent 独立核对原件后确认的单份 GT 明确错误（未剔除，因需主观判断）：把邮编标成
税号、把宛名标成开票方、把发票号填进税号字段等，估计再占 3–5%。

**③ prompt 仍可优化的空间 —— 有，但已呈明显递减**

`invoiceCode`（0%）、`billFromComposite`（27.5%）等字段仍有规则空间，但 v4/v5 的实测表明：
继续加规则会以牺牲实体检出为代价。乐观估计剩余空间 3–6pp，到不了 96%。

## 五、Prompt 改造内容（定稿版）

**剔除的他国/他语种规则**（已验证 0 残留）：印尼 Faktur Pajak 全段、越南/欧洲 `6.000=6000`
数字歧义、美国海关 CBP/ENTRY SUMMARY、Singtel 账单规则、泰语分支代码 `buyerBranchCode` 字段、
Záloha/Facture d'Avance/Vorkassenrechnung 等外语关键词、MM-DD-YY 歧义消解流程、多币种推断。

**注入的日本领域知识**：
- 和暦换算（令和N年=2018+N、平成N年=1988+N、R7/H31 缩写）
- 適格請求書発行事業者登録番号 T+13 位（含位数校验，防把 `〒2860106` 邮编误判为税号）
- 消費税 8%/10% 双税率、内税/外税区分、taxCategory 保留票面原文（不映射英文简称）
- 分类词表（請求書/領収書/領収証/ご利用証明書/レシート…）
- **实体切分口径**（9 条）：領収書与同票明細合并、請求書与明細書按合计判断是否合并、
  装订件只输出請求書、信用卡売上票不单独成条、竖排/旋转票必须计入、相同金额不去重
- **防幻觉规则**（7 条）：两阶段作业、位置可指认、禁止编号/日期外推、重复三元组检查、
  12 张上限自检、不确定输出 other
- **明细口径**：金额 net/gross 双填、articleName 剥前缀、「标签:值」信息行也输出、
  但し書き作为明细行、税汇总 0–1 条为主

## 六、结论与建议

**96% 在 qwen3-vl-plus + 当前 GT 上不可达。** 三个独立错因分析 agent 的天花板测算
（明细 ~82%、标量 ~95.5%，综合 ~90%）已经低于 96%；而实测成绩 52–62% 距那个天花板还有 30pp，
差距主要由模型的日文 OCR 精度造成。

已排除的路径：**加 prompt 规则**（v4/v5/v6 三次尝试均在 59–62% 徘徊，改善一处必损失另一处）、
**提高分辨率**（300 DPI 反降 3pp）、**换 Gemini**（本机网络成功率仅 52%，且即便可用字段准确率也只 +2.6pp）。

**已排除的还有**：把 prompt 指令语言换成英文（+0.08pp，远在噪声内）。

仍值得做的（按预期收益排序）：

0. **多次运行 + 自洽性投票**（新增，由噪声实验直接推导）。既然同一 prompt 两次运行漏检实体差 7 条，
   说明模型对混贴页的切分是"抖"的而非"盲"的——同一张票在某次运行里能被看见。跑 3 次后按
  （商家, 日期, 金额）三元组做并集去重，理论上能把漏检显著压下去，而漏检正是最大失分源
   （一条实体归零 = 7–10 个字段归零）。代价是 3 倍 token。这是目前唯一有明确机理支撑的提升路径。

1. **清洗 GT**（最高杠杆，也是让指标有意义的前提）。11 组重复原件的互斥标注、以及三个分析 agent
   逐张核对原件后定位的单份错标（把邮编 `〒2860106` 标成税号、把宛名标成开票方、把发票号填进税号
   字段、同一张票 `totalAmount` 一处标 2200 一处标 200）需要人工裁定统一口径。
   现有 `_bench/gt_conflicts.py` 已能自动列出全部冲突点，人工只需裁决。
2. **解决 Gemini 的网络可达性**（代理/中转），换取实体检出的质变：误检 27→4、漏检 7→4。
   这是 qwen3 六轮 prompt 迭代都没能做到的。
3. **明细数组单独设门槛**。它占考核字段的 35–58% 却只有 36–48%，且 GT 口径最不稳定
   （同一张票两份标注连拆行方式都不同）。标量与明细分开设指标更能反映真实能力。
4. **混贴页先切分再识别**（工程量较大）：用版面检测把台纸上的每张小票裁成独立图再逐张送模型，
   可同时消除漏检与幻觉——当前失分的最大单一来源。

## 七、复现方式

```bash
cd japan
PYTHONPATH=. python3 _bench/split_data.py          # 生成三分（去泄漏）
python3 _bench/gt_conflicts.py                     # 生成冲突标注清单
python3 _bench/score_jp.py selftest                # 打分器自检（应 100%）

# 跑一个变体（结果带缓存，重跑零成本）
../backend/.venv/bin/python _bench/run_jp.py run JP_invoice_receipt.yaml \
    --split val --tag v3-val --workers 5

# 打分（--clean = 剔除冲突标注口径）
python3 _bench/score_jp.py v3-val --split val --clean
python3 _bench/analyze.py v3-val --split val       # 失分聚类
```

**打分口径**（与需求方确认过）：字段级准确率 = 判对字段数 ÷ GT 有值字段总数；明细数组全部计入
（按集合最佳匹配逐子字段计分）；漏检实体其全部 GT 字段计 0；误检实体单独统计不进分母；
数字容差 0.01、日期归一 YYYY-MM-DD、文本 NFKC 全半角归一。
打分器 round-trip 自检 100%（GT 喂自己满分），扰动测试通过（改金额扣分、删实体计漏检）。
